# Rove4k 구현 계획: A–F 전체 구현과 후보별 독립 최적화

## 1. 구현 범위와 완료 기준

핸드오프의 A–F 여섯 계열을 모두 구현한다. 기존 C·Rust 비교 방침도 유지하므로, **각 계열의 핵심 기능이 동작하는 C·Rust 구현 총 12개**를 기본 구현 범위로 한다.

같은 언어 안에서 검증된 연산과 소스를 재사용할 수 있다. C와 Rust의 엔진 코어는 각각 구현하며, Rust 실행 파일이 C 엔진을 호출하는 방식으로 독립 구현을 대신하지 않는다.

A–F는 원래 서로 다른 설계축을 포함한다. 따라서 여섯 후보의 코드를 전부 복제할 필요는 없지만, **각 후보의 고유 경로가 실제 검색과 최종 실행 파일에 연결되어야 한다.** 기능 플래그, 빈 모듈, 테스트 전용 경로만 있는 상태는 해당 후보의 구현 완료로 인정하지 않는다.

| 계열 | 반드시 완성할 고유 구현 | 주된 제출 경로 |
|---|---|---|
| **A — 압축 소스·mailbox** | 작은 mailbox 상태, 증분 갱신, HCE, PVS·QS·TT, history·continuation·correction, SMP | 압축 소스 중심 일반 4K |
| **B — 전술 계산 공유** | bitboard+mailbox, 공격자 계산의 재사용, SEE, single singular, PVS·TT·SMP | 일반 4K 중심, ELF도 비교 |
| **C — 대상 네이티브·SIMD** | 실제 사용되는 SIMD 경로, 대상 ISA에 맞춘 상태·평가·전술 연산, 네이티브 빌드·복원, SMP | 압축 네이티브 일반 4K |
| **D — 작은 자체 복원 ELF** | 작은 시작 코드·OS 경로·복원기, 스칼라/HQ 기반 코어, HCE·PVS·TT·history·correction·SMP | **4K ELF 필수** |
| **E — 작은 학습 모델** | 데이터 준비, 학습, 양자화, 저장 표현, 실제 평가·ordering 연결, 시작 시 확장 또는 직접 실행 | 일반 4K·ELF 양쪽 평가 |
| **F — MTD(f)** | 반복 심화, zero-window 반복, lower/upper 관리, 수렴·중단·최선수 보존, 안정적인 정수 평가, SMP | 일반 4K·ELF 양쪽 평가 |

각 계열에서 적어도 하나의 언어·제출 경로가 4KiB 조건을 충족하도록 최적화한다. C와 Rust의 두 구현 모두 기능 검증과 실질적인 축소 비교를 수행하되, 두 언어가 모두 출품 크기를 충족해야만 언어 선택을 할 수 있는 것은 아니다.

전체 구현의 완료 조건은 다음과 같다.

- A–F 각각의 고유 기능을 포함한 실행 가능한 C·Rust 구현이 있다.
- 각 계열에 실제 크기 적격 제출물이 최소 하나 있다.
- 전체 포트폴리오가 일반 4K와 4K ELF 두 부문을 충족한다.
- 후보별 추가 기능과 제외 기능을 실제 크기·성능 근거로 설명할 수 있다.
- 선택된 제출 파일을 정본과 recipe에서 재생성할 수 있다.

어떤 계열이 크기 조건을 해결하지 못했다면 해당 항목을 미완료로 남긴다. 고유 기능을 제거해 다른 계열과 같은 엔진으로 만든 뒤 원래 후보를 완성했다고 기록하지 않는다.

## 2. 공유할 계약과 독립적으로 결정할 구현

공유 기반은 **행동 계약·검증·빌드 도구**에 집중한다. 모든 후보가 같은 보드 구조체, TT 레이아웃, 검색 함수 시그니처, 클래스 계층을 사용하도록 강제하지 않는다.

공통으로 유지할 내용은 다음과 같다.

| 공유 계약 | 후보별로 달라질 수 있는 구현 |
|---|---|
| 체스 규칙, 외부 좌표, 특수 수, 반복·반수 시계의 의미 | mailbox, bitboard, 혼합 표현, 진영 변환 |
| 점수 관점, mate 거리, bound와 완료 상태의 의미 | 점수 저장 폭, TT 구성, 검색 제어 |
| 4K 최소 UCI와 명령 경계 | 입력 함수, 출력 함수, 시작 코드 |
| 작업 게시·취소·완료·결과 수락·메모리 수명 | 원자 엔트리, 단일 소유, 슬롯, 큐, 그룹 |
| 단일 파일 크기·시작·외부 의존 조건 | 압축 소스, 압축 네이티브, 자체 복원 ELF |
| 정본과 재생성, 실험 입력의 식별 | 소스 결합, 생성, 인라이닝, 특수화, 배치 |

공통 기반을 바꾸면 영향을 받는 후보를 함께 확인한다. 반대로 특정 후보만 필요로 하는 기능을 공통 계층에 올려 모든 출품물에 비용을 추가하지 않는다.

빌드는 선택한 후보·언어·기능·자원·제출 형식에 필요한 소스만 결합한다. 출품 실행 파일에는 후보 선택기나 범용 플러그인 로더를 넣지 않는다. 개발용 후보 선택과 실험 관리는 엔진 밖에서 수행한다.

**출품용 UCI는 이전에 정한 최소 범위를 유지한다.**

- `uci`/`uciok`, `isready`/`readyok`
- `position startpos [moves …]`
- 시계가 포함된 `go wtime … btime … winc … binc …`
- 검색당 한 번의 `bestmove`
- `quit`와 입력 EOF 처리
- `stop`·`ucinewgame` 및 미지원 명령을 오류 없이 소비하는 처리

FEN, 깊이·노드 제한, 상세 통계, 자원 옵션, 진단 명령은 개발 빌드에 둔다. 실제 구현에 비용상 이점이 있을 때 추가 기능을 검토할 수 있지만, 일반 TCEC의 전체 UCI 요구를 4K 공통 의무로 추가하지 않는다. [TCEC 4K 전용 규칙](https://wiki.chessdom.org/TCEC_4k_Rules)

## 3. A–F별 구현 지시와 독립적인 발전 방향

### A — 압축 소스와 mailbox에 예산을 집중한다

첫 구현은 10×12 mailbox·copy-make로 작성한다. 이후 0x88/10×12와 copy-make/make-unmake 조합을 비교한다.

이동 생성·공격 판정의 방향 정보, 수 적용·위치 키·평가 갱신을 가능한 범위에서 공유한다. 별도 undo 코드가 더 크면 copy-make를 유지할 수 있다. 반대로 복사 비용이 many-core 성능을 제한하면 make/unmake로 전환한다.

A에서는 작은 핵심 연산으로 확보한 공간을 다음 기능에 우선 투자한다.

- continuation·follow-up·capture history
- pawn·material·non-pawn correction
- 작은 폰 구조·킹 안전 평가
- 저비용 PALS 힌트와 검색 다양화

이 기능들의 고정 순서를 정하지 않는다. 각 기능의 코드뿐 아니라 추가 hash·상태 갱신·초기화·저장 비용까지 포함해 조합을 선택한다.

### B — 공격자 계산을 여러 기능에서 재사용한다

bitboard와 mailbox의 일관된 갱신을 먼저 완성한다. 공격자 계산을 SEE·체크 판정·수 정렬·필요한 전술 조건에서 재사용한다.

SEE와 singular는 실제 검색에 연결한다. 특히 다음을 확인한다.

- 핀, 킹 포획 가능성, 앙파상, 승격을 포함한 SEE의 선언된 의미
- SEE를 정렬용으로 쓰는 경로와 pruning에 쓰는 경로의 구분
- singular 자격을 갖춘 TT 결과
- 같은 상태·같은 ply에서의 제외 검색
- 제외 검색의 결과가 정상 TT·학습 상태를 오염시키지 않는 처리

B는 공격자 연산을 이미 보유하므로, A보다 SEE·전술 pruning·추가 체크 확장이 저렴할 수 있다. 이 재사용 비용을 측정해 B만의 기능 구성을 발전시킨다.

### C — SIMD와 네이티브 표현을 실제 이점으로 연결한다

A 또는 B에서 검증된 연산을 출발점으로 삼되, 데이터 배치와 연산 경로를 네이티브 구현에 맞게 재구성한다.

평가 특징, 누적값, 수 점수, 공격 정보 등에서 실제 사용하는 SIMD 경로를 구현한다. 개발용 스칼라 참조와 대조하고, 생성된 코드에서 해당 경로가 사용되는지 확인한다.

AVX2를 실행 검증 가능한 기본 대상으로 삼고, AVX-512는 해당 ISA 환경에서 검증할 별도 빌드 후보로 둔다. 런타임 ISA 탐색 대신 빌드 프로필을 고정한다.

C의 추가 기능은 다음 비용 구조를 활용한다.

- 이미 존재하는 벡터 연산을 이용한 평가 특징
- 작은 모델의 정수 추론
- 연속 배치된 history·correction 처리
- TT·캐시 접근과 결과 게시 개선

SIMD 명령이 있다는 사실을 성능 향상으로 인정하지 않는다. 명령 길이·상수·정렬·압축 결과와 실제 검색 성능을 함께 측정한다.

### D — ELF 런타임과 복원기에서 절약한 공간을 엔진에 돌린다

자체 복원 ELF, 작은 시작 코드, 직접 OS 호출, 고정 작업 공간을 초기 구현부터 연결한다. SMP도 기준 구현에 포함한다.

슬라이딩 공격은 스칼라 방식과 HQ를 구현해 비교한다. 큰 테이블을 사용하지 않는 표현이 파일을 줄이는 대신 노드 비용을 늘리는지도 확인한다.

복원기와 엔진을 따로 최적화하지 않는다. 다음 조합을 완성 파일로 비교한다.

- 엔진 이미지 배치와 코드 공통화
- 데이터·코드의 압축 방식
- 선택 스트림에 특수화한 복원기
- 시작 코드·헤더·패딩
- 시작 시 테이블 확장과 직접 계산

D에서 절약한 공간은 continuation·correction·SEE·singular·모델·병렬 제어 중 실제 이득이 큰 기능에 재투자한다. 복원기가 작아졌다는 이유만으로 엔진 기능을 계속 고정하지 않는다.

### E — 학습부터 출품 추론까지 전 과정을 완성한다

E는 모델 인터페이스만 구현한 상태로 남기지 않는다. **학습 입력 고정 → 학습 → 양자화 → 저장 표현 선택 → 출품 추론 → 대국 검증**을 끝까지 연결한다.

첫 완성 범위에는 다음을 포함한다.

- 구조화한 작은 평가 모델과 선택적인 residual·상호작용
- 작은 ordering 모델
- 정수 추론과 점수 범위 관리
- 정확한 저장·복원과 시작 시 lookup 확장 후보
- 학습용·검증용·대국용 입력의 분리

더 작은 MLP 등은 이 기반에서 추가 비교한다. 평가 모델의 점수와 ordering의 우선순위를 구분하고, ordering 점수를 정상 TT bound로 사용하지 않는다.

양자화·특징 삭제·모델 구조 변경은 모델 실험으로 기록한다. 선택한 정수 모델을 다른 바이트 표현으로 저장하는 작업은 무손실 표현 실험으로 기록한다.

E에서는 큰 모델을 일괄 적용하는 대신, **추론 코드·특징 추출·가중치·복원기 전체를 합친 비용**으로 모델을 선택한다. 같은 모델도 A·B·C·D의 기존 연산에 따라 결합 비용이 다르므로 교차 후보를 만든다.

### F — MTD(f)의 수렴과 정보 재사용을 독립적으로 완성한다

MTD(f)를 PVS의 옵션 분기로만 추가하지 않는다. root 반복 제어, 첫 추정, lower/upper 유지, 최선수 보존, 중단 처리를 독립적으로 구현한다.

- 같은 깊이의 반복 probe 사이에서 유효한 범위를 유지한다.
- TT에서 두 방향의 bound를 보존하는 표현과, 더 작은 TT 표현의 비용을 비교한다.
- 직전 깊이·같은 홀짝 깊이의 결과를 첫 추정에 사용하는 후보를 비교한다.
- zero-window라는 이유만으로 모든 노드에 PVS의 non-PV pruning을 적용하지 않는다.
- 마감으로 수렴하지 못한 깊이는 완료로 인정하지 않는다.
- bound가 충돌했을 때 범위를 임의로 맞추거나 임시 수렴으로 처리하지 않는다.

첫 기준 구현은 고정된 정수 평가로 만든다. correction·학습 상태를 추가할 때는 probe 사이에 평가 의미가 바뀌지 않도록 스냅샷·갱신 경계·TT 재사용 조건을 함께 설계한다.

F는 반복 probe 비용을 줄이는 TT·수 정렬·첫 추정에 더 많은 예산을 사용할 수 있다. 다른 후보와 같은 평가·history 구성을 유지하기 위해 F에 필요한 비용을 제한하지 않는다.

## 4. 병렬 후보도 실제 구현한다

many-core 설계는 각 엔진을 완성한 뒤 남는 공간에 추가하는 기능으로 취급하지 않는다. 모든 계열은 초기부터 병렬 검색·시간·종료를 포함해 설계한다.

다음 병렬 계열도 실제 검색에서 동작하는 구현을 마련한다.

| 병렬 계열 | 완료할 동작 |
|---|---|
| **느슨한 공유** | 워커별 독립 상태, TT 공유, 검색 다양화, 완료 결과 선택 |
| **명시적 분할** | root 작업 배정·재배정, 완료·bound 집계, 중단된 조각 처리 |
| **그룹·지역성** | 그룹별 작업·메모리·TT 정책과 그룹 간 정보 공유 |
| **PALS** | 반례 힌트, 호환되는 부분 결과 재사용, 제안–반박–Repair |
| **혼합 정책** | 관측된 상태·비용에 따라 서로 다른 작업 방식을 실제로 선택하는 제어 |

모든 A–F × 모든 병렬 방식 × 모든 포장을 무조건 전수 구현·검증하는 곱집합은 만들지 않는다. 다만 병렬 방식마다 적어도 하나의 완성 엔진에 통합하고, 후보와의 결합 비용을 확인한다. C·Rust 비교에서는 같은 병렬 기능을 맞춘 실험도 확보한다.

PALS는 ordering-only 구현에서 끝내지 않는다. 세 범위를 모두 구현한다.

1. **반례 힌트:** 조사할 응수·위치를 전달한다.
2. **정상 부분 결과:** 위치·깊이·평가·window·bound 계약이 맞는 완료 결과를 재사용한다.
3. **제안–반박–Repair:** 같은 첫 수를 유지한 복구와 후속 검토를 수행한다.

제한된 수순의 반박을 root 첫 수 전체의 반박으로 사용하지 않는다. 역할별 평가·선택성이 다르면 결과를 자동으로 같은 bound로 섞지 않는다. 새 질문마다 원래 예산을 다시 지급하지 않으며 모든 작업은 원 deadline에 종속된다.

작은 구현에서는 작업 문맥을 빌드·세션 단위로 고정해 반복 검사 비용을 줄일 수 있다. 그 전제가 성립하지 않는 조합에서는 필요한 구분을 유지한다.

출품 자원은 빌드 상수로 고정한다. 512개 검색 스레드까지 활용 가능한 구조를 만들고, 256·509·512 등의 고정 프로필을 비교할 수 있게 한다. 메인·제어·보조 작업까지 실제 총수를 계산한다. 전체 메모리와 초기화 비용도 포함한다.

512개 워커를 만들었다는 사실과 512개 하드웨어 스레드에서 유효한 확장을 달성했다는 사실은 별도로 검증한다.

## 5. 후보별 바이트 예산을 재투자하는 최적화 절차

비교를 **구조 비교와 최종 후보 비교**로 나눈다.

**구조 비교에서는 기능을 맞춘다.** 같은 평가·검색 기능·자원에서 보드, 언어, 상태 갱신, 런타임, 포장의 비용을 분리한다. 이 단계는 어느 기반이 어떤 기능을 저렴하게 제공하는지 알아내는 데 사용한다.

**최종 후보 비교에서는 기능 구성을 자유롭게 한다.** 각 후보가 같은 4KiB 제한과 실행 조건 안에서 가장 좋은 결과를 내도록 서로 다른 기능을 추가·교체·개선한다.

후보별 최적화 반복은 다음으로 고정한다.

1. 현재 기능 조합으로 실제 최종 파일을 만든다.
2. 소스·코드·데이터·복원기·시작·RAM·검색 비용을 기록한다.
3. 그 후보에서 결합 비용이 작은 기능을 추가하거나 기존 기능을 개선한다.
4. 전체 파일을 다시 축소·압축하고 실제 크기와 성능을 확인한다.
5. 유리한 후보들을 남기고 조합·상호작용을 비교한다.
6. 선택한 조합을 정본과 recipe로 재생성한다.

다음 원칙을 적용한다.

- 남은 예산은 **4,096바이트에서 현재 완성 파일 크기를 뺀 값**으로 계산한다.
- 기능 비용은 개별 소스 줄 수가 아니라 완성 파일의 전후 차이로 잰다.
- 기존 공격자·특징·hash·decoder를 재사용하는 기능은 결합 후 비용을 측정한다.
- 개별 기능의 크기 차이를 단순 합산해 조합 비용으로 사용하지 않는다.
- 작은 기능만 고르지 않는다. 큰 기능 하나가 작은 기능 여러 개보다 유리할 수 있다.
- 단독 효과가 작아도 다른 기능의 비용을 줄이는 기반은 조합 후보로 유지한다.
- 한 후보에서 실패한 기능을 다른 후보에서도 자동 제외하지 않는다.

예를 들어 A는 추가 history·correction을, B는 공격자 기반 전술 기능을, C는 벡터 평가·모델을, D는 복원기 절약분으로 추가 검색 기능을, E는 모델과 특징의 균형을, F는 TT와 수렴 제어를 더 발전시킬 수 있다. 이것은 초기 탐색 방향이며 영구적인 기능 배정표는 아니다.

교차 개선도 수행한다. B의 공격자 계산에 E의 특징을 얹거나, C의 정수 SIMD에 E의 모델을 결합하거나, D의 포장에 더 큰 검색 코어를 넣는 식으로 새 완성 후보를 만든다. 출처가 되는 A–F 기준 구현과 합성 후보를 구별해 결과를 기록한다.

## 6. 소스 축소·포장·언어 비교의 실행 기준

모든 후보에서 다음을 실제로 검토한다.

- 개발 기능·일반 파서·범용 컨테이너·포맷팅 제거
- 중복 상태와 갱신 코드 축소
- 함수 공통화·인라이닝·선택적 중복·상수 인자 특수화
- 루프·방향 표·진영 변환
- 평가·모델 데이터의 정확한 저장 표현
- 시작 시 생성·확장과 직접 계산
- 작은 시작 코드·고정 작업 공간·스레드 수명
- 언어별 안전한 토큰 처리·재명명·상수 표기·배치
- 컴파일러·링커·codec·loader의 완성 파일 비교

**C와 Rust의 언어 선택은 계열별로 수행한다.** A에서 C가 작았다는 이유로 E나 F의 Rust 구현을 생략하지 않는다. 또한 같은 기능에서의 언어 차이와, 각 언어에서 예산을 최대한 활용한 최종 엔진의 차이를 구분한다.

압축 소스·압축 네이티브·자체 복원 ELF를 모두 구현하되, 각 후보의 주된 경로를 먼저 완성한다. 이후 다른 제출 형식으로 옮겼을 때의 이득을 비교한다.

NVCompact의 기존 표기 축소 경로가 오브젝트 동일성을 요구하는 경우, 기계어가 바뀌는 구조 변경은 별도 엔진 후보로 입력한다. 기존 검사를 약화해 구조 변경을 표기 변경으로 통과시키지 않는다.

원본 보존 후보도 계속 유지한다. 더 짧은 소스가 더 큰 압축 파일을 만들거나, 더 작은 기계어가 더 느린 검색을 만들 수 있으므로 어느 중간 지표도 최종 승자를 대신하지 않는다.

정본·생성 입력·필요한 도구는 유지하고 생성물만 직접 수정하지 않는다. UB, 데이터 레이스, 잘못된 정수 연산, 의미가 다른 점수의 혼합은 크기 최적화로 인정하지 않는다.

## 7. 검증·비교·채택 기준

후보마다 다음 상태를 따로 기록한다.

| 상태 | 충족해야 할 내용 |
|---|---|
| **기능 구현 완료** | 고유 알고리즘이 실제 엔진 경로에서 실행되고 관련 검증을 통과함 |
| **크기 적격** | 필요한 코드·데이터·설정·헤더·복원기를 포함한 단일 파일이 4,096바이트 이하임 |
| **프로필 실행 확인** | 해당 워커·TT·ISA·OS에서 시작·검색·종료·메모리를 확인함 |
| **성능 근거 확보** | 선언한 환경과 예산에서 대국·확장성 비교를 수행함 |

공통 검증은 합법 수, 특수 수, 반복·반수 시계, 위치 키, 점수·mate·bound, 시간 제한, 최종 UCI, 결과 게시, 작업 종료와 자원 회수를 다룬다.

후보별로 다음 검증을 추가한다.

- **A:** 증분 상태와 재계산의 일치, continuation·correction 갱신의 자격.
- **B:** 공격 정보·SEE의 경계 사례와 singular 제외 검색의 상태 보존.
- **C:** 스칼라·SIMD 대조, 누산 범위, 정렬, 대상 ISA 실행.
- **D:** 정확한 복원, ELF 로딩, 외부 프로그램 미사용, 시작·정리.
- **E:** 데이터 분리, 모델 버전, 양자화·정수 추론·저장 복원의 구분.
- **F:** probe 간 bound 유지, 수렴, 중단, 평가 안정성, 마지막 완료 결과.
- **병렬 구현:** 오래된 작업·미완료 결과·불일치 문맥의 수락 방지와 실제 작업 재배정.

최종 대국에서는 **각 후보가 자기 예산 안에서 발전시킨 기능 조합**을 비교한다. 기능을 맞춘 실험의 승자만으로 최종 엔진을 선택하지 않는다.

어떤 후보가 작지만 약하거나, 강하지만 시작·크기 조건을 만족하지 못하면 그 상태를 그대로 기록한다. 충분한 기력 근거가 없으면 최소 크기 후보와 추천 후보를 같은 의미로 발표하지 않는다.

## 8. 작업 순서, 계산 예산과 최종 산출물

작업은 다음 순서로 진행한다.

1. **공통 계약·검증·빌드 기반을 마련한다.** 개발 인터페이스와 출품 인터페이스를 분리하고 후보별 전체 비용을 측정할 수 있게 한다.
2. **A–F의 최소 완성 구현을 모두 만든다.** 일부 후보의 조기 우세를 이유로 나머지를 중단하지 않는다.
3. **C·Rust 대조를 완료한다.** 각 계열의 고유 기능과 필수 정확성을 양쪽에서 확인한다.
4. **병렬 계열을 실제 통합한다.** 힌트·정상 부분 결과·Repair까지 포함한 경로를 구현한다.
5. **후보별 독립 최적화를 반복한다.** 절약한 바이트를 후보별 기능과 조합에 재투자한다.
6. **유망한 교차 후보를 만든다.** 재사용 가능한 연산과 포장을 결합하고 완성 파일을 다시 비교한다.
7. **최종 제출물과 추천 구현을 선정한다.** 일반 4K·ELF별로 적격성과 성능 근거를 구분해 정리한다.

외부 계산 정책은 기존 결정을 유지한다. **Spot 우선, 필요 시 On-Demand 전환, 전체 누적 12시간·부대비용 포함 120달러 상한**이다. 후보 수가 늘었다고 이 예산을 후보마다 새로 부여하지 않는다.

로컬·CI에서는 전체 후보의 기능·구조 검증과 작은 자원 비교를 진행한다. 외부 자원은 큰 메모리·워커 검증, 후보 선별, 최종 파일 대국에 배분한다. 기존의 최대 128개 색상 교환 쌍도 전체 예산 안의 상한으로 유지한다.

계산 예산이 부족하면 전체 후보의 구현을 생략하지 않는다. 성능 비교가 미완료인 후보와 검증 범위를 명시하고, 부족한 근거를 전체 순위나 TCEC 실전 우위로 확대하지 않는다. AWS 192vCPU 실행은 TCEC의 512하드웨어 스레드 실행과 구분한다.

최종 산출물은 다음과 같다.

- A–F의 C·Rust 정본과 재생성 가능한 빌드·축소 recipe.
- 각 계열의 크기 적격 제출물과 고유 기능 설명.
- 후보별 기능 구성, 전체 파일 크기, 시작·메모리·워커·성능 근거.
- 기능을 맞춘 구조 비교와 후보별 최적 기능 조합 비교.
- 교차 후보의 구성과 채택·미채택 근거.
- 일반 4K·4K ELF의 추천 파일, SHA-256, 재생성 방법, 확인하지 못한 범위.

정식 릴리스의 추천 파일을 소수로 정하더라도 **전체 후보의 완성 구현과 검증 가능한 빌드 프로필은 유지**한다. 이후에는 새 기능이나 축소 방법이 생겼을 때 기존 탈락 후보도 다시 발전시킬 수 있게 한다.
